# packaging

Only what Tauri's own bundle settings (`desktop/src-tauri/tauri.conf.json`) do not cover.

## macOS

| Piece | Where |
|---|---|
| App bundle and DMG, with `harmflowd` as a sidecar and the built-in agents and skills as resources | `make app` → `desktop/src-tauri/target/release/bundle/` |
| The local app's installed copy, which `make update-app` replaces | `~/Applications/HarmFlow.app`, or `$INSTALL_DIR/HarmFlow.app` |
| The daemon as a launchd user agent (`com.harmflow.daemon`), written only when the user turns autostart on | Generated by the daemon itself (`daemon/internal/adapters/launchd`), in `~/Library/LaunchAgents/` |
| The tray starting with the session | `tauri-plugin-autostart`, a launch agent that opens the app with `--hidden` |
| Signing with a Developer ID and notarization | Not done yet: the certificate does not exist. Until then builds are unsigned and Gatekeeper asks for confirmation on first open |

## Updating the local app

`make update-app` (`packaging/macos/update-app.sh`) runs `main` as the local app in one command. The local app is one
installed copy, `~/Applications/HarmFlow.app`, or `$INSTALL_DIR/HarmFlow.app` when `INSTALL_DIR` is set; `make app`
builds into `target/` and installs nothing.

1. It refuses, with nothing changed, off `main`, with uncommitted changes, or when `git pull --ff-only origin main`
   cannot fast-forward. Then it runs `make app`; a failed build leaves the window, the daemon, and the installed copy
   as they were.
2. It finds the daemon of `$HARMFLOW_HOME`, or of `~/Library/Application Support/HarmFlow`, through that directory's
   `run/daemon.json`, never by process name, so the daemons of other data directories (the e2e one, a worktree's
   development one) are never touched.
3. It copies the build beside the installed copy, then stops that daemon through `POST /api/v1/daemon/stop`, without
   `force`. While executions run, the daemon refuses and so does the update: the window, the daemon, and the installed
   copy stay as they were.
4. It quits the window of the installed copy, or of this checkout's `target/release` build, where it ran before the
   app was installed. Only then does it replace the installed copy, by moving the old one aside and the new one in.
5. It restores what it found, from the installed copy. A daemon that was running starts again, through
   `launchctl kickstart` when the launch agent `com.harmflow.daemon` serves that data directory, and must answer with
   the new commit. A window that was open reopens. What was stopped stays stopped, unless `make update-app OPEN=1`:
   then the daemon and the window start also when they did not run, the daemon first, as the window only offers to
   start a daemon that is down.

### The launch agent

The daemon writes `~/Library/LaunchAgents/com.harmflow.daemon.plist` with its own executable when Autostart is turned
on, and launchd keeps the program it loaded until the next login. When the agent serves the data directory:

- and its plist runs a `harmflowd` other than the installed one, such as a build in `target/` from before the app was
  installed, `make update-app` refuses before stopping anything and names that binary. To move the agent: turn
  Autostart off in Settings, which deletes the plist; run `make update-app` again, which starts the installed
  `harmflowd`; then turn Autostart on, which writes the plist with it.
- and its plist runs the installed `harmflowd` but launchd loaded another one before the plist changed, the daemon
  starts directly, outside launchd, until the next login.

The script never edits, unloads, or kickstarts an agent that runs another binary. `make test-packaging` covers these
cases with a fake `launchctl` and a fake plist.
