# packaging

Only what Tauri's own bundle settings (`desktop/src-tauri/tauri.conf.json`) do not cover.

## macOS

| Piece | Where |
|---|---|
| App bundle and DMG, with `harmflowd` as a sidecar and the built-in skills as resources | `make app` → `desktop/src-tauri/target.noindex/release/bundle/` |
| The local app's installed copy, which `make update-app` replaces | `~/Applications/HarmFlow.app`, or `$INSTALL_DIR/HarmFlow.app` |
| The daemon as a launchd user agent (`com.harmflow.daemon`), written only when the user turns autostart on | Generated by the daemon itself (`daemon/internal/adapters/launchd`), in `~/Library/LaunchAgents/` |
| The tray starting with the session | `tauri-plugin-autostart`, a launch agent that opens the app with `--hidden` |
| Signing with a Developer ID and notarization | Not done yet: the certificate does not exist. Until then builds are unsigned and Gatekeeper asks for confirmation on first open |

## Updating the local app

`make update-app` (`packaging/macos/update-app.sh`) runs `main` as the local app in one command. The local app is one
installed copy, `~/Applications/HarmFlow.app`, or `$INSTALL_DIR/HarmFlow.app` when `INSTALL_DIR` is set; `make app`
builds into `target.noindex/` and installs nothing.

1. It refuses, with nothing changed, off `main`, with uncommitted changes, or when `git pull --ff-only origin main`
   cannot fast-forward. When the pull changed `update-app.sh`, it runs the new one in its place, once, before it stops
   or builds anything: bash has already read the old one. Then it reads `running` from `GET /api/v1/stats` of the
   daemon of step 2, and says so when executions run, since the restart will be refused unless they end first.
   Then it runs `make app`, unless the build is already of the pulled commit: `make app` writes the commit it built
   beside the bundle, in `target.noindex/release/bundle/macos/HarmFlow.app.commit`, once the build succeeds.
   `make update-app FORCE_BUILD=1` builds anyway. A failed build leaves the window, the daemon, and the installed copy
   as they were.
2. It finds the daemon of `$HARMFLOW_HOME`, or of `~/Library/Application Support/HarmFlow`, through that directory's
   `run/daemon.json`, never by process name, so the daemons of other data directories (the e2e one, a worktree's
   development one) are never touched.
3. It copies the build beside the installed copy, then stops that daemon through `POST /api/v1/daemon/stop`, without
   `force`. While executions run, the daemon refuses and so does the update: the window, the daemon, and the installed
   copy stay as they were, and the new build is not running. `make update-app WAIT=1` waits instead: every 5 seconds
   it says how many executions run, and it asks again, still without `force`, once none does, so an execution that
   starts in between is waited for too, never cancelled. After `WAIT_TIMEOUT` seconds, 3600 by default, it gives up
   with the same refusal.
4. It quits the window of the installed copy, or of this checkout's build in `target.noindex/release`. Only then does
   it replace the installed copy, by moving the old one aside and the new one in.
5. It restores what it found, from the installed copy. A daemon that was running starts again, through
   `launchctl kickstart` when the launch agent `com.harmflow.daemon` serves that data directory, and must answer with
   the new commit. A window that was open reopens. What was stopped stays stopped, unless `make update-app OPEN=1`:
   then the daemon and the window start also when they did not run, the daemon first, as the window only offers to
   start a daemon that is down.

### The launch agent

The daemon writes `~/Library/LaunchAgents/com.harmflow.daemon.plist` with its own executable when Autostart is turned
on, and launchd keeps the program it loaded until the next login. When the agent serves the data directory:

- and its plist runs a `harmflowd` other than the installed one, such as a build in this checkout from before the app
  was installed, `make update-app` refuses before stopping anything and names that binary. To move the agent: turn
  Autostart off in Settings, which deletes the plist; run `make update-app` again, which starts the installed
  `harmflowd`; then turn Autostart on, which writes the plist with it.
- and its plist runs the installed `harmflowd` but launchd loaded another one before the plist changed, the daemon
  starts directly, outside launchd, until the next login.

The script never edits, unloads, or kickstarts an agent that runs another binary. `make test-packaging` covers these
cases with a fake `launchctl` and a fake plist.

### Launching by name

Every build makes a `HarmFlow.app` with the same bundle identifier, and macOS registers each one with Launch Services:
this checkout's release and debug builds, every worktree's build, the `/Volumes/dmg.*` volumes that
`bundle_dmg.sh` mounts while making the DMG. Which one opens by name is up to Launch Services. So after installing,
`make update-app` runs `lsregister -f` on the installed copy and `lsregister -u` on every registration of that
identifier that is in this checkout's Cargo output or whose path no longer exists, naming each one. It leaves
registered the bundles that exist elsewhere, such as another worktree's build, and deletes no file.

Unregistering alone does not last: a bundle in a folder that Spotlight indexes is registered again. So Cargo writes to
`desktop/src-tauri/target.noindex`, set in `.cargo/config.toml`: Spotlight skips a folder whose name ends in `.noindex`,
or starts with a dot, as `.worktrees/` does. `make update-app` also unregisters the bundles of the `target/` that Cargo
wrote to before, and names it to delete, since it stays indexed while it exists.
`make test-packaging` covers which registrations it removes, with a fake `lsregister`.

To check that `open -a HarmFlow` starts the installed copy, with another bundle on the machine:

1. Build a debug bundle of this checkout, so a second `HarmFlow.app` exists, and register it, without opening it,
   which would attach it to the real data directory: `cd desktop && pnpm tauri build --debug`, then
   `/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister -f
   src-tauri/target.noindex/debug/bundle/macos/HarmFlow.app`.
2. Quit every HarmFlow window, from the tray or with Command-Q: `open -a` only brings forward a copy that runs.
3. Run `make update-app` on `main`. It prints
   `unregistered …/target.noindex/debug/bundle/macos/HarmFlow.app (a build in this checkout)`.
4. Run `open -a HarmFlow`, then `ps -axww -o comm= | grep harmflow-desktop`: the window's executable is
   `~/Applications/HarmFlow.app/Contents/MacOS/harmflow-desktop`.
